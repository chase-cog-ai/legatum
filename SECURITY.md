# Security policy

## Reporting a vulnerability

Please report suspected vulnerabilities privately through GitHub's
[private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)
("Security" tab, "Report a vulnerability") rather than a public issue. You will get an acknowledgement
within a few days. This is a hobby project without a bug bounty.

## Scope

Legatum is a static web app (served by Cloudflare Pages) with the Rust engine compiled to WebAssembly. It has no server program and installs nothing. The network surfaces are the online relay and the game upload Worker:

- Online play (`plans/online-play.md`, `infra/relay/README.md`): the game runs in the host's browser tab, which dials out over wss to a Cloudflare Worker that lists games and copies messages. The lobby is public: anyone can list rooms and open guest sockets, and the relay cannot tell a seat token from other text, so seat tokens and game messages stay between guest and host. The game id is random and the per-turn hash sent to guests is the state hash masked with a per-game secret key the host never sends, so a guest cannot test guesses at hidden state (for example a short map seed) against either. Because any stranger can take an open seat, a host can lock a game with a join code (4 to 12 letters or digits; guests type it once) and can remove a player from a seat. The code stays in the host's tab and is never sent to the relay, which learns only that the game is locked; a connection gets 5 wrong codes before the host closes it, a connection holds one seat, and a removed seat stays closed until the host opens it. A short code does not stop a script that keeps reconnecting, so a host who cares picks 8 or more characters. The relay enforces its own limits, with no dashboard setup: 256 rooms in all; 8 live rooms per network (an IPv4 /24 or IPv6 /48); per client address (an IPv6 address counts as its /64 network), 2 live rooms, 6 room creations per 10 minutes and 4 guest sockets per room; 8 guests per room; message size caps; and per-socket message and byte rate caps that close a flooding guest or host tunnel (code 4029). Client addresses are kept only as salted hashes, for as long as the room, socket or 10-minute rate window lasts, and are never logged. The public game list never shows text a host typed: each room is listed under two fixed words and a number picked by its room id, and the build label must be one the game makes. A host that sends keepalive frames and then goes silent for 60 s leaves the list, and `LOBBY_OPEN=0` stops new rooms at once while running games carry on. Filling the lobby now takes many addresses, and a zone rate-limiting rule covers `relay.playlegatum.com` and `games.playlegatum.com` (`infra/relay/README.md`, Edge rule); if that is still not enough, tighten the rule or add a shared secret on room creation.
- Game uploads (`infra/games/README.md`): the hosted web build sends each game's record, with every seat under its default name, to a Cloudflare Worker that stores it in a private R2 bucket. The Worker accepts only allow-listed page origins, locks each game to the random per-game upload key its first keyed upload carried (SHA-256 stored with the object; a checkpoint under another key is refused with 409, so a game id from a shared save cannot overwrite a record; a game first stored without a key stays open until a keyed checkpoint arrives), caps bodies (2 MiB gzipped, 16 MiB unpacked), refuses any other seat name, accepts only the factions, difficulties, engine commits (40 hex digits) and game start times the game writes, keeps no request log, and allows each client address 50 new games per UTC day, each network (IPv4 /24, IPv6 /48) 200, and all addresses together 50000 (it keeps only a salted hash of the address, cut to the /64 for IPv6, for the current day, inside a Durable Object). Anyone who can script a request from an allowed origin can store well-formed junk up to those caps; that is an accepted risk. The Worker validates a record's metadata and coach answers only, so its tape and telemetry can hold any text: the Mac analysis job gives its reviewer facts with no tools, and an agent with tools reads only checked whole numbers (`tools/games/analyse_games.py telemetry`), never a raw record.

## Data kept on your computer

The game keeps data only in your browser: autosaves and game histories (IndexedDB and local storage) and the files you choose to download (saves and exported game histories). Clearing site data removes them. Nothing is written elsewhere on your computer.

In scope: the relay and upload Workers' request handling, the host's handling of guest messages, and save loading (malformed files must fail cleanly and never overwrite a good save). Out of scope: attacks that need control of the player's browser or machine.
